# ADR 033: CIにPostgreSQLを立て、DBを使うテストとマイグレーションの検証を毎回実行する

## ステータス
決定済み

## 背景
- 現在のCI(`.github/workflows/ci.yml`)が実行しているのは、BEの`go build`・`go vet`と、FEの
  `lint`・`build`だけで、**`go test`は1度も実行していない**。コンパイルは確かめているが、動作は
  確かめていない
- ADR031で、AI提案の二重生成を防ぐ排他制御のテスト(`advice_concurrency_test.go`)を追加した。
  このテストは実際のPostgreSQLの行ロックに頼る性質を確かめるため、DBが必要で、
  `TEST_DATABASE_URL`が無いとスキップされる。CIにはDBが無いので、**CIでは実行されず、排他制御を
  壊す変更をしても、CIは緑のままになる**(ADR031のレビューでの指摘)
- ADR032で、本番DBへのマイグレーション適用は手動と決めた。一方、CIの中に作る使い捨てのDBは、
  壊れても何も失われないため、自動で適用してよい。両者は対象のDBが違い、矛盾しない

## 検討した選択肢
- **A: 現状維持(DBを使うテストは手元でだけ実行する)**: 手間は増えないが、ADR031のテストが
  CIの守りにならない
- **B: GitHub Actionsのサービスコンテナで、PostgreSQLを起動する(採用)**: CIの実行中だけ
  PostgreSQLが立ち上がり、終わると破棄される。ローカルの`docker-compose.yml`と同じ構成を、
  CIの中で再現するだけである
- **C: DBを使わないテストに書き直す**: repositoryをダミーに差し替える。排他制御は、DBが
  行ロックで順番に処理する性質に頼っており、ダミーでは確かめられない。また、repositoryは
  インターフェース化していない(docs/architecture.md 7.)
- **D: テスト用に、本番とは別のSupabaseプロジェクトへ接続する**: 外部サービスへの依存、
  接続文字列の管理、無料枠の消費、実行の遅さが増える
- **E: テストの中からDBコンテナを起動するライブラリ(testcontainers-go等)を使う**: ローカルとCIで
  同じ仕組みで動くが、BEの依存が増える。今の規模には過剰である

## 決定
Bを採用する。CIに`backend-test`のジョブを追加し、次を実行する。

1. `postgres:16`のサービスコンテナを起動する(ローカルの`docker-compose.yml`と同じ版)
2. `golang-migrate`(ローカルと同じv4.20.1に固定)で、`backend/migrations/`の全マイグレーションを
   空のDBに適用する
3. `up`→`down -all`→`up`を行い、すべての`down`のファイルも正しく動くことを確かめる
4. `TEST_DATABASE_URL`を指定して、`go test ./...`を実行する

既存のジョブ(`Backend (Go build & vet)`、`Frontend (lint & build)`)は変えない。ジョブ名の変更で、
既存のチェックの名前が変わるのを避けるため、別のジョブとして追加する。

## 理由
1. ローカルと同じ構成なので、「手元では通るのにCIでは通らない」差が出にくい
2. BEの依存が増えない
3. 使い捨てのDBで、本番のSupabaseには一切接続しない。テストの接続先は、`localhost`以外なら
   失敗するようにしてある(`newTestPool`)
4. 全マイグレーションを毎回、空のDBに適用するため、新しいマイグレーションを足したときは
   自動で対象になり、ワークフローの修正が要らない。マイグレーションのファイルが壊れていれば、
   マージ前に気づける

## 影響・トレードオフ
- CIの実行時間が、PostgreSQLの起動とテストの分だけ増える
- CIのDBは、本番のSupabaseと同一ではない(PostgreSQLのバージョンや、Supabase固有の拡張・設定が
  違いうる。本番のバージョンは確認していない)。見つけられるのは、ロジックとマイグレーションの
  ファイルの正しさまでで、Session poolerなど本番の接続設定の問題は見つけられない
- CIのDBのパスワードは、使い捨てのコンテナ専用の値で、秘密情報ではない
- `go test ./...`は、DBを使わない既存のテスト(AIクライアント・目標service・エラー文変換)も
  あわせて実行する。これらもCIで初めて実行される
- 今後DBを使うテストを書くときは、`TEST_DATABASE_URL`を使い、`localhost`以外に繋がない
  決まりを守る
- Goのデータ競合検出(`-race`)は、今回は入れない。DBの競合ではなく、Goのメモリの競合を
  検出するもので、必要になった時点で追加する
