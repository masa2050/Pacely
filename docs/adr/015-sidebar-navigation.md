# ADR 015: サイドバーナビゲーション・設定画面の実装方針

## ステータス
決定済み

## 背景
フェーズ7-2として、記録/目標/AI提案/設定を行き来できるサイドバー(またはハンバーガーメニュー)の追加と、
退会機能を目立たない位置(Dashboardの一番下)から独立した「設定」画面へ移動することが要件定義された。
現状のフロントエンドはルーティングライブラリを導入しておらず、`App.tsx`の`useState`による簡易な画面切り替え
(プライバシーポリシー・パスワード再設定で採用済み)のみで構成されている。

## 検討した選択肢

### ナビゲーション方式(記録/目標/AI提案)
- **A: 別画面に分割し、サイドバーのリンクで画面遷移する**: 各画面がシンプルになるが、Dashboard.tsxを
  記録/目標/AI提案の3画面に分割する必要があり、実装コストが大きい。また7-2の要件に明記された
  「Dashboard.tsxのJSX構造(カードの並び順)は変えない」という制約と矛盾する
- **B: Dashboard内の既存カードへのアンカースクロールとする**: 画面分割をせず、`<a href="#id">`で
  該当カードへスクロールするだけで済む。Dashboard.tsxの構造を変えずに済み、実装コストも小さい

### 設定画面への遷移方式
- **A: react-router-domを新規導入し、`/settings`等のパスを持たせる**: URLでの直接アクセス・ブラウザの
  戻る/進むに対応できる一方、この1画面のためだけに新規依存を追加することになり、CLAUDE.mdの
  過剰設計を避ける方針に反する
- **B: 既存のuseStateベースの画面切り替えパターンを踏襲する**: プライバシーポリシー・パスワード再設定
  画面と同じパターンで実装でき、新規依存が増えない

### プロフィール編集の配置
- **A: Dashboardのプロフィールカードに編集フォームを残したまま、設定画面にも同じ編集フォームを追加する**:
  要件文言(「設定画面にプロフィール編集をまとめる」)には近いが、同じ編集ロジック(地域の保存処理)が
  2箇所に重複し、保守性が落ちる
- **B: Dashboardのプロフィールカードは表示専用にし、編集(地域の変更)は設定画面に一本化する**:
  編集ロジックが1箇所になり、要件文言の「まとめる」という意図にも合致する。Dashboard.tsx側は
  カードの並び順・カード自体は変えず、カード内の編集フォームのみ削除する変更に留まる

### サイドバーの表示方式(初版→修正)
- **A(初版で採用): SP幅はハンバーガーメニュー、PC幅(1024px〜)では常時表示の固定サイドバー**:
  実装してみたところ、PC幅でサイドバー分の横幅を専有してしまい、後述のダッシュボード3カラム表示が
  必要以上に狭くなる問題が発生した。ユーザー確認の結果、そこまでの常時表示は不要という判断になった
- **B(修正後に採用): SP/PC共通で、ヘッダーの「Pacely」文言の左にハンバーガーボタンを置き、
  クリックでドロップダウン表示する**: 常時表示領域を持たないためダッシュボードの横幅を圧迫せず、
  実装もAより単純(PC幅用の固定表示CSSが不要)

### ダッシュボードPC3カラム表示の実装方法(初版→修正)
- **A(初版で採用): CSS Gridの`grid-template-areas`で、AI提案カードを2行分にrow-spanさせる**:
  実装してみたところ、CSS Gridは同じ行にある全列で行の高さを共有する仕様のため、内容量の差が
  大きいカード(AI提案は長文になりやすい)が同じグリッドの行に混在すると、内容の少ない列(プロフィール・
  ランニング記録側)に大きな空白ができてしまった。列幅も均等割りにしたため、表を含む目標設定カードが
  狭くなり文字が読みにくい問題も発生した
- **B(修正後に採用): 既存カードを列ごとにグルーピングするラッパー(`dashboard__column`)を追加し、
  Flexboxで3列を横並びにする**: 各列の高さがその列の中身だけで決まるため、内容量の差があっても
  空白ができない。SP幅では`dashboard__column`を`display: contents`にしてbox-treeから消し、
  これまで通りカードが縦一列に並ぶ見た目に戻す

## 決定
- ナビゲーション方式はB(記録/目標/AI提案はアンカースクロール)を採用
- 設定画面への遷移方式はB(react-router-dom不使用、既存の画面切り替えパターンを踏襲)を採用
- プロフィール編集の配置はB(Dashboardは表示専用、編集は設定画面に一本化)を採用
- サイドバーはSP/PC共通でハンバーガーボタン+ドロップダウンとして実装する(常時表示の固定サイドバーは
  不採用に変更)
- ダッシュボードPC3カラム表示は、CSS Gridではなくラッパーdiv+Flexboxで実装する
- 退会機能はDashboard.tsxから新設の`Settings.tsx`に移動する

## 理由
1. Dashboard.tsxを画面分割せずアンカースクロールにすることで、7-2の「JSX構造(カードの並び順)は
   変えない」という実装方針をそのまま守れる
2. 個人開発のMVPで設定画面1枚のためだけにルーティングライブラリを導入するのは過剰設計(CLAUDE.md方針4)。
   既存のプライバシーポリシー・パスワード再設定と同じ画面切り替えパターンを踏襲すれば一貫性も保てる
3. 編集フォームを1箇所(設定画面)に一本化することで、地域の保存ロジックの重複・表示ズレ(片方だけ
   更新されて他方が古いままになる等)のリスクを避けられる
4. サイドバーを常時表示にしない方が、PC幅でのダッシュボード横幅を圧迫せず、実装もシンプルになる
5. CSS Gridの行共有仕様はカード間の内容量の差を吸収できないため、列ごとに高さが独立するFlexboxの
   方がこのダッシュボードの実際のコンテンツ(長文になりがちなAI提案・表を含む記録/目標)に適している

## 影響
- `frontend/src/components/Sidebar.tsx`(新規)、`frontend/src/components/Settings.tsx`(新規)を追加
- `frontend/src/components/Dashboard.tsx`から退会カード・プロフィール編集フォームを削除し、
  プロフィールカードは表示専用にした。また各カードを`dashboard__column`でグルーピングし、
  ヘッダー内に`Sidebar`を埋め込んだ(`onSettingsClick`をpropsで受け取る)
- `frontend/src/App.tsx`に`showSettings`のstateを追加し、`showPrivacyPolicy`と同様のパターンで
  設定画面を表示する。`Sidebar`は`Dashboard`のヘッダー内で描画するため、`App.tsx`側では直接レンダリングしない
- `frontend/src/App.css`にハンバーガーメニューのドロップダウン表示用CSS、PC幅(1024px〜)での
  ダッシュボード3カラム表示用のFlexbox CSSを追加(CSS Gridの`grid-template-areas`は不採用)
- ユーザーネーム編集は`users`テーブルに`username`カラムが無いため7-2では未実装。7-3でカラム追加・
  API対応後にあわせて実装する
