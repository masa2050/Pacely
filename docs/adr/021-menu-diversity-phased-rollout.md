# ADR 021: 練習メニュー多様性改善(8-2)を段階的に導入する

## ステータス
決定済み

## 背景
docs/implementation-plan.md 8-2の通り、実データで5回連続して「目標レースペースのペース走/調整走」
が提案される問題が確認された。原因は3つ特定済み:

1. プロンプトに前回までの提案メニューが入っていない
2. `next_menu`のスキーマ(`{distance_km, pace_sec_per_km, note}`)がペース走以外を表現できない
3. プロンプトに今日の日付・レースまでの残日数が無い

対策として①(前回提案メニューをプロンプトに渡す)②(`next_menu`にメニュー種別を追加)
③(日付・残日数を渡す)の3つが挙がっているが、これを1つのブランチ・1回の変更でまとめて
実装するか、段階的に分けて実装するかを決める必要があった。

## 検討した選択肢
- **A: ①②③を1ブランチでまとめて実装する**: 完了条件(メニューの種別または強度が変化すること)を
  1回の検証で確認できるが、もし効果が出なかった場合にどの対策が効いていない/効いているのかの
  切り分けが難しい。3つの変更が絡み合った状態でのADRの説明・レビューも複雑になる
- **B: ①②③を段階的に分けて実装する**: 各ステップごとに生成結果を見て効果を確認しながら進められる。
  ただし①③はプロンプト文字列の追加のみで`model.NextMenu`の型定義・DB保存・FE表示には影響しない一方、
  ②(`next_menu`へのメニュー種別追加)は`model.NextMenu`の型定義・DBのjsonb内容・FEの表示コンポーネント
  すべてに影響するため、②を含むステップは変更範囲が広くなる

## 決定
Bを採用する。実装順序は **① → ③ → ②**とする。

- ステップ1(①): 直近の提案履歴(`next_menu`)をプロンプトに渡し、「前回と違う刺激を与える」ことを
  AIに明示する
- ステップ2(③): 今日の日付・レースまでの残日数をプロンプトに渡す
- ステップ3(②): `next_menu`にメニュー種別(ジョグ/ペース走/インターバル/ロング走/休養)を追加する

## 理由
1. ①③はどちらもプロンプト文字列(`buildPrompt`の入力)を増やすだけで、`model.NextMenu`の型・
   DBのjsonb列構造・フロントエンドの表示コンポーネントには一切影響しない。まず①③だけで
   AIの出力が変化するかを安全に確認できる
2. ②は`model.NextMenu`の型定義変更→DB保存内容の変更→FE表示の変更まで連鎖する、8-2の中で
   最も変更範囲が広い対策。①③を先に試すことで、②に着手する前に「スキーマを変えずに
   プロンプト側の工夫だけでどこまで改善するか」を見極められ、②の設計(メニュー種別の
   列挙値をどう決めるか等)にもその結果を反映できる
3. ①→③の順にしたのは、8-2の「原因」の記述順で①が最も直接的(AIが自分の過去の提案を
   知らない)と説明されており、次に③(日付情報が無く練習の位置づけを判断できない)が
   独立した軽微な追加のため。②より先に軽い変更から着手し、各ステップで生成結果を見ながら
   段階的に進める
4. 温度(temperature)を上げる対応は8-2の記述で明示的に否定されているため選択肢から除外した

## 影響
- 8-2全体の完了条件(「連続して生成したアドバイスで、練習メニューの種別または強度が変化すること」)は
  ステップ3(②)の完了をもって満たされる想定。ステップ1・2の時点では「強度・距離の変化」までは
  見込めるが、「種別」の変化(休養日・インターバル等の提案)はスキーマ上まだ不可能なため
- ステップ2(②)完了時に`docs/database.md`の`advices.next_menu`のjsonb構造を更新する
  (CLAUDE.mdルール7)
- 各ステップは独立して動作確認・コミットする(CLAUDE.mdルール1・10)。ブランチは8-2全体で
  1本(`feature/phase8-2-menu-diversity`)とし、ステップごとにコミットを分ける
