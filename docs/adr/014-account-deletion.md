# ADR 014: 退会機能(アカウント削除)の実装方針

## ステータス
決定済み

## 背景
フェーズ6でプライバシーポリシーを作成するにあたり、「データの削除を求める権利」を明記する必要があった。
当初は「開発者へ個別連絡→手動削除」という運用を想定していたが、本番デプロイして他人が使える状態にする以上、
手作業での対応は現実的でなく、セルフサービスの退会機能をデプロイ前に実装することにした。

## 検討した選択肢

### 削除範囲
- **A: アプリ側データ(users/runs/goals/advices)のみ削除し、Supabase Authのログイン情報は残す**:
  実装は簡単だが、再ログインすると`GetOrCreateMe`により空のプロフィールが再作成されてしまい、
  「退会した」という状態にならない(ログイン自体はできてしまう)
- **B: アプリ側データに加えて、Supabase Auth側のアカウントも管理者APIで削除する**: 本来の「退会」の
  期待(二度とそのメール/パスワードでログインできない)に応えられる。ただしSupabaseの`service_role`
  キー(強い権限を持つ管理者キー)をバックエンドに新たに持たせる必要がある

### 削除順序
- **A: Supabase Auth削除→DB削除**: Auth削除後にDB削除が失敗すると、そのユーザーは二度と
  ログインできず、削除リクエストも二度と送れないため、DBに孤立データが永久に残るリスクがある
- **B: DB削除→Supabase Auth削除**: DB削除を先に済ませておけば、Auth削除に失敗してもまだ
  ログインできるため再度「退会する」を実行できる。DB側は`DELETE FROM users`を冪等に実装しているため
  再実行しても問題ない

### 子テーブルの削除方法
- **A: アプリ(service層)でruns→advices→goals→usersの順に手動でDELETEを発行する**: 削除順序を
  間違えるとFK制約違反になり、テーブルが増えるたびに削除処理の修正が必要になる
- **B: FKに`ON DELETE CASCADE`を設定し、`DELETE FROM users`一発で連動削除させる**: DB側で
  整合性を保証できるため、アプリ側の実装・保守が単純になる

## 決定
- 削除範囲はB(Supabase Authアカウントも削除)を採用
- 削除順序はB(DB削除→Auth削除)を採用
- 子テーブル削除はB(`ON DELETE CASCADE`、migrations/000005)を採用
- `internal/service/user.go`の`DeleteAccount`に実装し、`DELETE /users/me`(要JWT認証)から呼び出す

## 理由
1. プライバシーポリシーで「削除できます」と明記する以上、実装が伴っていないと規約が実態と合わなくなる
2. 個人開発でDB削除とAuth削除にまたがる分散トランザクションを厳密に実装するのは過剰設計(CLAUDE.md
   方針)。その代わり「失敗時にどちらの状態に倒すか」を明確にすることで、複雑な補償処理無しに
   安全側に倒せるようにした
3. `ON DELETE CASCADE`はPostgresの標準機能であり、追加の依存を増やさずにテーブル横断の削除漏れを防げる

## 影響
- `backend/.env`に新たに`SUPABASE_SERVICE_ROLE_KEY`が必須環境変数として追加された
  (Supabaseダッシュボード > Project Settings > API から取得)。他の必須キーと同様、未設定だと
  起動時に落ちる
- `docs/database.md`のFK定義に`ON DELETE CASCADE`の注記を追加(migrations/000005)
- `docs/api.md`に`DELETE /users/me`を追加
- フロントエンドのプライバシーポリシーページには「アプリ内の退会機能から削除できる」旨を記載する
  (開発者への個別連絡を前提とした記述は撤回)
