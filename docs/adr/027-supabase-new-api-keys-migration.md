# ADR 027: Supabaseのservice_roleキーを新しいAPIキー方式(secret / publishable)に移行する

## ステータス
提案中(移行作業は未実施。ローカルでの動作確認後に「決定済み」へ更新する)

## 背景
2026-10-21(UTC)、Railwayから「環境変数を保存するシステムに不正アクセスがあり、一部は復号された
可能性がある」という通知が届き、Railwayに置いていたシークレットをすべて入れ替えることになった
(経緯は`docs/devlog.md` 2026-10-25の項目)。

その中で、Supabaseの`service_role`キー(退会・パスワード変更でSupabase Authの管理者APIを呼ぶために
BEが持っている、RLSを無視できる強い権限のキー。ADR014・ADR016)を無効化しようとしたところ、
このキーは単体では再発行できないことが分かった。

- レガシーの`anon`/`service_role`キーは、旧JWT Secretで署名されたJWTそのものである
- 本プロジェクトはすでに新しいJWT署名鍵(ES256。ADR005でBEのトークン検証に使っている方式)に
  移行済みで、ダッシュボード上で旧JWT Secretを作り直す操作ができない
- Supabaseの画面では「publishable / secret APIキーに切り替えて、レガシーキーを無効化する」ことが
  案内されている

なお、ADR014で`service_role`キーを導入した際は、キーの方式(レガシーか新方式か)を比較検討しておらず、
当時のダッシュボードで取得できたレガシーキーをそのまま使っていた。

## 検討した選択肢
- **A: レガシーキーのまま使い続ける**: 作業は不要だが、漏洩した可能性のある`service_role`キーを
  無効化する手段がない。RLSを無視してDB・Authを操作できるキーを有効なまま残すことになる
- **B: 新しいAPIキー方式に移行し、レガシーキーを無効化する(採用)**: BEは`sb_secret_...`、
  FEは`sb_publishable_...`を使う。キーを個別に作成・削除できるため、今後漏洩しても
  その1本だけを入れ替えられる
- **C: service_roleキーを使う機能(退会・パスワード変更)をやめる**: キー自体が不要になるが、
  ADR014・ADR016で決めた機能要件を満たせなくなる

## 決定
Bを採用する。手順は「新しい値を用意 → 利用側で動くことを確認 → 古い値を失効」の順に行う。

1. Supabaseで`sb_secret_...`と`sb_publishable_...`を作成する
2. ローカルの`.env`を新しいキーに差し替え、ログイン・パスワード変更・退会(テスト用アカウント)を確認する
3. Vercelの`VITE_SUPABASE_ANON_KEY`をpublishableキーに変えて再デプロイし、本番のログインを確認する
4. Railwayの`SUPABASE_SERVICE_ROLE_KEY`をsecretキーに変えて再デプロイし、本番のパスワード変更を確認する
5. 3・4の確認後に、レガシーキーを無効化する

## 理由
1. 漏洩した可能性のある`service_role`キーを無効化する方法が、Bしかない
2. キーを個別にローテーションできる方式にしておくと、次に同じことが起きたときに
   「1本の入れ替えのためにanonキーまで変わる」といった巻き添えが起きない
3. 今回の障害(devlog 2026-10-25)は、反映できることを確かめる前に古い値を失効させたことで起きた。
   同じ失敗を避けるため、ローカル→本番→失効の順を手順として固定した

## 影響・未確認事項
- `backend/internal/service/user.go`は、キーを`apikey`ヘッダーと`Authorization: Bearer`ヘッダーの
  両方に入れて管理者APIを呼んでいる。`sb_secret_...`はJWTではないため、`Authorization`ヘッダー側で
  受け付けられるかは未確認。手順2で失敗した場合は、`apikey`ヘッダーのみで呼ぶようにコードを修正する
  (その場合は機能ブランチで修正し、本ADRに結果を追記する)
- 環境変数名(`SUPABASE_SERVICE_ROLE_KEY`・`VITE_SUPABASE_ANON_KEY`)は変更しない。中身の形式が
  変わるだけで、名前を変えるとFE/BE・ドキュメントの修正範囲が広がるため
- ユーザーのログイントークンの検証(ADR005、JWKS/ES256)は、この移行の影響を受けない
