# ADR 022: next_menuにsegments構造を導入し、まずビルドアップ走のみ対応する

## ステータス
決定済み

## 背景
8-2②(ADR 021)で`next_menu`に`menu_type`(ジョグ/ペース走/インターバル/ロング走/休養)を
追加したが、8-2の元々の原因分析(docs/implementation-plan.md 8-2)で名指しされていた
「インターバル・ビルドアップを表現できない」という問題のうち、対策の列挙値からビルドアップ走が
漏れていた。

さらにユーザーとの相談で、以下が明確になった。

1. **インターバル走**は現状`distance_km`/`pace_sec_per_km`(単一の数値ペア)のみで、
   本数(reps)・1本あたりの距離・レスト時間を表現できない。これらは`note`の自由記述任せで、
   AIが書くかどうかも粒度も保証されない
2. **ビルドアップ走**(1回の練習内でペースを徐々に上げる)は、単一の`pace_sec_per_km`では
   原理的に表現不可能。5つの列挙値のどれにも当てはまらない、明確な抜け
3. **変化走・ウェーブ走**(ペースが複数回入れ替わる)も同様に単一ペースでは表現できないが、
   Pacelyの目標種目(`full_marathon`/`half_marathon`/`10km`/`5km`)のうち5km・10kmは
   相対的にスピード練習の比重が高いと考えられ、本当に必要かどうかはまだ判断材料(実際の
   生成結果)が無い

これらは共通して「1回の練習が複数の区間(セグメント)で構成される」という同じ性質の問題であり、
種別ごとに専用フィールド(`interval_reps`、`build_up_paces`等)を都度追加すると、docs/database.md
5.で意図していた「jsonbで柔軟に対応する」方針に反して場当たり的なスキーマ膨張になる。

## 検討した選択肢

- **A: 現状維持(noteの自由記述のみ)**: 実装コストは無いが、本数・レスト・ペース変化がAIの
  気分次第でしか出てこず、8-2②の完了条件(メニューの種別・強度の変化)を強度面で満たせない
- **B: 種別ごとに専用フィールドを追加**: `interval_reps`・`interval_rest_sec`のような
  フィールドをその都度追加する。実装は小さく済むが、ビルドアップ・変化走・ウェーブ走で
  また別のフィールドが必要になり、フィールドが種別の数だけ増え続ける
- **C: `next_menu`に`segments`配列を追加し、共通構造で表現する**:
  `segments: [{reps, distance_km, pace_sec_per_km, rest_sec}]`を持たせ、インターバルも
  ビルドアップも変化走も同じ構造(区間のリスト)で表現する。1回作れば、将来変化走・
  ウェーブ走・インターバルの本数詳細化を追加する際にスキーマ変更が不要になる

## 決定
Cを採用する。ただし**今回の実装で実際に`segments`を使う(AIに出力させる)のはビルドアップ走のみ**とする。

- `model.NextMenu`に`Segments []MenuSegment`(jsonb、`omitempty`)を追加
  - `MenuSegment{Reps int, DistanceKm float64, PaceSecPerKm float64, RestSec float64}`
  - `Reps`は同じ内容を何本繰り返すか(通常1。将来インターバルの本数詳細化に使う想定)
  - `RestSec`はその区間の後の休憩秒数(通常0。将来インターバルのレストに使う想定)
- `menu_type`に`ビルドアップ走`を追加(`model.MenuTypeBuildUp`)。プロンプトでは
  「2〜4個の`segments`を、距離の合計が`distance_km`と一致するように、ペースが
  徐々に上がる順で出力すること」と指示する
- 既存の`distance_km`(合計距離)・`pace_sec_per_km`(代表ペース)は**そのまま残す**。
  `segments`は「詳細な内訳」の追加情報という位置づけで、無くても(古い提案・
  ビルドアップ走以外)今まで通り距離・ペース・合計時間の表示だけで成立する
- **インターバルの本数・レスト詳細化、変化走・ウェーブ走の追加は今回のスコープ外**とする。
  インターバルは実際の生成結果で`note`の記述が不十分だと分かった時点で、変化走・ウェーブ走は
  5km/10km目標での生成結果を見てから、それぞれ改めて判断する(このADRで設計した
  `segments`構造はそのまま再利用できるため、追加時に新しいADRは不要と想定)

## 理由
1. ビルドアップ走は「単一ペースで表現不可能」という他の4種別には無い性質を持つ、
   最も明確な抜けだったため優先して対応する
2. インターバルの本数・レスト詳細化と変化走・ウェーブ走は「あった方が良いが、今どれだけ
   困っているか実データで確認できていない」ため、先に列挙値だけ増やすとAIの選択肢が
   広がるだけで実際に使われるかは賭けになる(CLAUDE.mdの過剰設計をしない方針)。
   `segments`という受け皿さえ用意しておけば、必要になった時にプロンプトと
   `menu_type`の追加だけで済み、再度のスキーマ設計は不要
3. `distance_km`/`pace_sec_per_km`を残すのは、既存のFE表示(距離・ペース・合計時間の
   統計欄)・DBの古い提案データとの後方互換のため。`segments`はあくまで追加情報として
   任意で足すことで、変更範囲をFEの「詳細内訳を追加表示する」部分だけに限定できる
4. `Reps`・`RestSec`をビルドアップ走の時点では使わない(常に1・0)としつつも型に含めるのは、
   将来インターバルに同じ構造を再利用する前提を型として先に固定しておくため。使わない
   フィールドを持つコストは小さく、後から追加する方が(②の`menu_type`同様)影響範囲が広い

## 影響
- `docs/database.md`の`next_menu`の例に`segments`(任意)を追記する
- FE(`AdviceView.tsx`)は`segments`が存在する場合のみ、区間ごとの内訳を追加表示する。
  存在しない場合(ビルドアップ走以外・②以前の古い提案)は現状の表示のまま
- AIが`segments`の距離合計と`distance_km`を一致させない、`reps`/`rest_sec`に
  ビルドアップ走で無関係な値を入れてくる、といった不整合は8-1/8-2②と同じ方針
  (エラーにせずログにのみ残す)で扱う
