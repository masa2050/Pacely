# ADR 031: AI提案の二重生成を、DBの条件付きUPDATEによる生成リースで防ぐ

## ステータス
決定済み

## 背景
`GET /advices/latest`(docs/adr/004)は、呼ばれたときに「前回の生成から24時間以上経っているか」を
判定し、必要ならAIを呼んで`advices`に保存する。この処理は次の順で動く。

1. 最新の提案を読む(`GetLatestByUser`)
2. 24時間以上経っていれば「生成が必要」と判断する
3. 天候API・AI APIを呼ぶ(10〜30秒、最悪で約100秒)
4. `advices`にINSERTする

1の「確認」と4の「保存」の間に隙間があり、その間は何も守られていない。この間に別のリクエストが
1を実行すると、そのリクエストもまだ古い提案を見て「生成が必要」と判断し、AIを呼んで保存する。
確認した時点の状態が、保存するときには古くなっている(check-then-act競合、TOCTOU)。

この競合は、複数タブを開く操作だけでなく、通常の使い方でも起きうる。
`Dashboard.tsx`で`AdviceView`の`key`に`runs.length`と`activeGoal.id`が入っており、初回表示で
記録と目標が順に届くたびに`AdviceView`が作り直されて、最大3回`GET /advices/latest`が送られる
(docs/implementation-plan.md 9-6 課題A)。

2026-11-03、ローカルのDBに対して再現テスト
(`backend/internal/service/advice_concurrency_test.go`)を書いて確認した。同じユーザーに5件の
リクエストを同時に送ると、**AIの呼び出しが5回、`advices`の保存が5件**になった(期待値はどちらも1)。

実害は次のとおり。

- AI APIの無料枠を、1ユーザーの操作で複数回分消費する。悪意があれば、全ユーザーの提案を止められる
- 同じ日の提案が履歴に複数並ぶ
- 重複した提案が「前回までの提案」としてプロンプトに入り、メニューの多様性(docs/adr/021)が下がる

面接で「多重ログインを制限していないので、複数タブで同時にAI提案を押すと、1日に複数の提案が
生成できるのでは」と指摘された。指摘は正しい。ただし、守るべきものはログインの数ではない。
**「1ユーザーにつき24時間に1回だけ生成する」というサーバー側のルール**を、同時リクエストでも
崩れないようにすることが本質である。

## 検討した選択肢
- **A: Goのプロセス内mutex(`sync.Mutex`、`singleflight`)**: ユーザーごとに排他する。
  実装は最も簡単。ただし効くのは同じサーバープロセスの中だけで、Railwayでインスタンスが2台に
  なったときや、デプロイ中に新旧のプロセスが並行して動くときには破れる
- **B: PostgreSQLのadvisory lock**: DBが持つ名前付きのロック。複数プロセスにまたがって効く。
  ただし生成の間(最大約100秒)、DB接続を1本握り続ける。接続数に余裕のない構成
  (docs/adr/030のSession pooler)では、同時に生成するユーザーが増えると他のAPIが詰まる
- **C: 生成リース(条件付きUPDATE)(採用)**: `users`に「生成中の期限」を持たせ、
  1文のUPDATEで取り合う。DB全体で効き、接続も握り続けず、プロセスが落ちても期限切れで解放される
- **D: 多重ログイン(1ユーザー1セッション)の制限**: Supabaseでは有料プランでの機能で、
  仮に使えても、1つのセッションからの並行リクエストは防げない。自分のフロントエンドだけでも
  3回送っているため、解決しない
- **E: 後続のリクエストをサーバー側で待たせ、完了後に結果を返す**: FEの変更は不要になる。
  ただし生成が失敗したとき、待っていた全員が順番にAIを呼び直し、障害時にAI呼び出しを増幅させる

## 決定
Cを採用する。

- `users`に`advice_lock_until timestamptz`(NULL許可)を追加する(migrations/000008)
- 生成の前に、次のUPDATEで「生成する権利」を取る。1行更新できれば取得成功、0行なら他のリクエストが
  生成中である

```sql
UPDATE users SET advice_lock_until = now() + interval '3 minutes'
WHERE id = $1 AND (advice_lock_until IS NULL OR advice_lock_until < now())
```

- `GetLatest`の流れを次のように変える。

  1. 記録件数・有効な目標の確認(従来どおり)
  2. 最新の提案が24時間以内なら、そのまま返す(従来どおり)
  3. 生成する権利を取る。**取れなければ、AIを呼ばずに`status: "generating"`を返す**
  4. **権利を取れたら、最新の提案をもう一度読む**(double-checked locking)。権利を待つ間に別の
     リクエストが生成を終えていることがあるため。24時間以内になっていれば、生成せずにそれを返す
  5. 生成して保存する
  6. 成功・失敗のどちらでも、最後に権利を返す(`advice_lock_until`をNULLに戻す)

- 手順6は、リクエストのコンテキストではなく、別のコンテキストで実行する。ブラウザが切断されて
  リクエストが中断されても、権利が3分間残らないようにするため
- 権利を返すときは、**自分が取ったときの期限と一致する場合だけ**消す
  (`WHERE advice_lock_until = <取得時の期限>`)。生成が長引いて期限が切れ、別のリクエストが
  新しく権利を取っているときに、その権利まで消して二重生成を招くのを防ぐ(/code-review指摘)
- 権利を取る前に、`users`の行の存在を保証する(`GetOrCreateMe`)。更新が0行のとき、
  「他のリクエストが生成中」と「行が無い」を区別できず、行が無いのに`generating`を返し続けるため
- 権利を取ってからの処理全体(再確認・DB読み出し・天候API・AI・保存)に、権利の期限より短い
  上限(2分30秒)を付ける。DBの読み書きにはタイムアウトが無く、固まると期限を超えて別の
  リクエストが権利を取れてしまうため
- `LatestAdviceResult.status`に`generating`を追加する。FEは数秒後に取り直す
- FEは、初回の取得を1回にする。`AdviceView`の`key`で作り直される仕組みをやめ、記録と目標の
  読み込み後に取得する(これは無駄なリクエストを減らす対策で、防御の本体はBEである)

## 理由
1. 確認と書き込みを**1文のSQLで同時に行う**ため、2つのリクエストが同時に来ても、PostgreSQLが
   行ロックで順番に処理し、片方だけが1行更新に成功する。Cのmutexに相当する排他を、DB全体で
   実現できる(compare-and-set)
2. 期限付きなので、サーバーが生成の途中で落ちても、権利が永久に残らない。期限の3分は、
   天候API(10秒)+Gemini(全体で90秒、docs/adr/025)の最悪値の約100秒に余裕を足した値
3. DB接続を生成の間じゅう握らないので、docs/adr/030の構成(接続数が少ない)でも問題にならない
4. 新しいテーブルを作らず、`users`に列を1つ足すだけで済む。「過剰設計をしない」方針に合う
5. 「生成中」を明示的に返すので、生成が失敗したときに待っていた全員がAIを呼び直す(Eの問題)ことが
   ない。次に取り直すかどうかはFEが決める

## 影響・トレードオフ
- **ADR004の補足になる**。ADR004では、生成を「いつ行うか」(記録追加時か取得時か)は比較したが、
  「取得時に生成するとして、GETで行うかPOSTで行うか」は比較していなかった。GETは、ブラウザや
  ライブラリが安全に再送・先読みしてよいメソッドとして扱われる(safe)。そこに副作用を持たせた
  ことで、同時リクエストで冪等性(何回呼んでも1回呼んだのと同じ状態)が崩れた。今回の修正は、
  GETのままで、冪等性を取り戻すものである。取得(GET)と生成(POST)の分離は、別のADRで改めて
  検討する
- 生成に失敗した場合も権利を返すため、ユーザーは「再読み込み」で、すぐにやり直せる
- **生成中のリクエストは、24時間以上前の古い提案があっても、それを見せずにスピナーだけを返す**。
  古い提案を目印付きで返す案(/code-review指摘)もあるが、「24時間経った提案は古い」という
  判断を画面側にも持ち込むことになるため、今回は見送った。また、生成が失敗した場合は、
  ポーリング中の各タブが次の取得で再び生成を試みる。ただし生成できるのは同じユーザーにつき
  同時に1件だけで、1回の失敗ごとにAIを呼ぶのは1回なので、修正前よりAIの呼び出しは増えない。
  障害が長引くようなら、失敗後の一定時間は再試行しない待機(クールダウン)を検討する
- FEは、記録・目標の初回読み込みが終わってから`AdviceView`を表示するため、AI提案の表示が
  その分だけ遅れる。`AdviceView`の`key`に`runs.length`を残しているのは、記録の追加や目標の
  変更に応じて提案を取り直すためで、生成中に取り直されても、権利があるので二重生成にはならない
- このADRを書いた時点では、CIには`go test`も、DBを使うテストも入っておらず(`TEST_DATABASE_URL`が
  無いとスキップ)、この排他制御のテストは、手元のローカルDBでだけ動いていた。
  **後日の補足**: ADR033で、CIにPostgreSQLを立て、このテストを毎回実行するようにした。CIで
  `TEST_DATABASE_URL`が無い場合は、スキップではなく失敗にしている
- `GET /advices/latest`のレスポンスに新しい`status`の値が増えるため、`docs/api.md`と
  `docs/database.md`を更新する
- リースの期限(3分)より生成が長引いた場合は、別のリクエストが権利を取れてしまう。ただし、
  外部APIの合計タイムアウト(約100秒)がリースより短いので、通常は起きない
- 本番への適用順序: **先に**マイグレーション000008を本番DBへ手動で適用し(ADR006)、
  **その後に**コードをデプロイする。列はNULL許可なので、適用中の旧コードには影響しない
- 検証: 再現テスト(`TestGetLatestConcurrentRequestsGenerateOnce`)が、修正前の「AI5回・保存5件」から
  「AI1回・保存1件」になることで確認する
- このADRの範囲外(別のADRで扱う)
  - 目標を変えても、24時間以内は古い目標向けの提案が返る問題(9-6 課題B)
  - GETと生成(POST)の分離
