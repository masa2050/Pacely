# ADR 009: 新規目標作成時、既存のactive目標は常にabandonedへ自動更新する

## ステータス
決定済み

## 背景
フェーズ3(目標設定機能)で`POST /goals`を実装するにあたり、docs/api.md 2.3には次のように書かれている。

> 作成時、既存のactive目標があればバックエンド側でstatusをabandonedまたはachievedに更新してから新規作成する(同時に有効な目標は1件のみという制約をservice層で担保する)

ここで「abandonedまたはachieved」のどちらに倒すかが未確定だった。バックエンドは新規目標作成のリクエストだけから「ユーザーが前の目標を達成したのか、諦めたのか」を判別する情報を持たない。

## 検討した選択肢
- **A: リクエストボディに`previous_goal_status`のような追加フィールドを持たせ、フロントから明示的に指定させる**: 意図を正確に反映できるが、`POST /goals`のI/Fが複雑になる。docs/api.mdにもそのようなフィールドの記載はない
- **B: 常にabandoned(断念)として扱う。「達成」にしたい場合は、新規作成の前に`PATCH /goals/{id}/status`で明示的にachievedへ更新してもらう運用にする**: `POST /goals`のI/Fはdocs/api.md記載のまま変更不要。達成・断念の意味の切り分けはUI側の操作順(先にachievedにする/しない)に委ねる

## 決定
Bを採用する。`GoalRepository.CreateAsNewActive`は、既存のactive目標があれば無条件でabandonedへ更新してから新規INSERTする。ユーザーが目標を達成した上で次の目標に進みたい場合は、フロント側で先に「達成にする」ボタン(`PATCH /goals/{id}/status`)を押してからでないと「新しい目標を設定する」フォームでの作成に進めない、という前提のUIにする。

## 理由
1. docs/api.mdが定義する`POST /goals`のリクエスト形(goal_type/target_time_sec/target_date)を変更せずに済む。将来AI提案機能(フェーズ5)がこのAPIを使う際もシンプルな形のままにできる
2. 「達成」は本来ユーザーが明示的に宣言する行為であり、新規目標作成という別の操作のついでに推測すべきではない。誤って「断念」も「達成」もどちらもtrueになりうる曖昧な状態を作らない
3. 実装は`GoalRepository.CreateAsNewActive`内のトランザクション(UPDATE→INSERT)で完結し、service層以上に分岐ロジックを持ち込まずに済む

## 影響
- FE(GoalList)では、active目標に対して「達成にする」「断念する」ボタンを常に表示し、ユーザーが目標を切り替える前にどちらかを選べるようにする
- 万が一ユーザーが「達成にする」を押さずに新しい目標を作成した場合、古い目標は自動的にabandoned(断念)として履歴に残る。これは意図した仕様であり、バグではない
