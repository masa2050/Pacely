# ADR 019: AIアドバイスへのフィードバックを`advices`テーブルのカラムとして持つ

## ステータス
決定済み

## 背景
フェーズ7-5(`docs/implementation-plan.md`)で、表示中のAIアドバイスに対して
「役に立った / 役に立たなかった」+任意コメントを送信できるようにする。
これはフェーズ7が掲げる「AI提案(コア機能)の精度を上げるためのフィードバック基盤」の
第一歩であり、将来的には「前回のメニューは不評だった」といった情報をプロンプトに
渡す使い方を想定している。

実装計画では保存先を「`advices`にカラム追加」か「`advice_feedbacks`テーブル新設」の
どちらにするか未決(要検討・ADR化)としていたため、ここで決定する。

前提として、`advices`の1レコードは1ユーザーに紐づく(他人が評価することはない)ため、
アドバイスとフィードバックの関係は**厳密に1:1**である。

## 検討した選択肢

### A: `advices`に評価用カラムを追加する
`is_helpful` / `feedback_comment` / `feedback_at` を既存テーブルに足す。

- 利点: 1:1なのでJOINも追加クエリも不要。`GET /advices/latest`・`GET /advices`の
  レスポンスにそのまま乗るため、フロントエンドは「このアドバイスを評価済みか」を
  追加のAPI呼び出し無しで描画できる。追加コードはマイグレーション1本と
  repositoryのUPDATE1本で済む
- 欠点: 「AIが生成したもの」と「ユーザーが入力したもの」が同じ行に同居する。
  大半の行で評価カラムはnullになる(疎なカラム)。評価軸を増やす・評価の変更履歴を
  残す、となると設計変更が必要

### B: `advice_feedbacks`テーブルを新設する
`advice_id`にUNIQUE制約を張って1:1を担保する。

- 利点: 関心の分離ができ、`advices`はAI生成物のまま保てる。評価軸の追加や履歴化に強い。
  「不評だったアドバイス一覧」のような分析クエリが書きやすい
- 欠点: 関係が1:1なのにテーブルを分けるのはMVPに対して過剰(CLAUDE.md方針4)。
  model / repository が1セット増え、アドバイスを返すすべての経路にJOIN
  (またはN+1回避のための追加クエリ)が付いて回る

## 決定
**Aを採用**し、`advices`に以下の3カラムを追加する(migrations/000007)。

| カラム名         | 型          | 説明                                                  |
| ---------------- | ----------- | ----------------------------------------------------- |
| is_helpful       | boolean     | true=役に立った / false=役に立たなかった / null=未評価 |
| feedback_comment | text        | 任意コメント(未入力時はnull)                          |
| feedback_at      | timestamptz | フィードバック送信日時(未評価時はnull)                |

- 評価値は`boolean`とする。現時点の要件が2値しかないため、varchar+CHECKやsmallintの
  段階評価は使わない拡張性になる
- APIは `PUT /advices/{id}/feedback`(冪等・上書き)の1本のみ。評価の取り消し
  (未評価に戻す`DELETE`)は今回のスコープに入れない。誤タップは逆の評価を押し直せば
  修正できるため、完了条件を満たすのに不要
- 他ユーザーのアドバイスへの送信は403で弾く(`docs/api.md`のエラー方針どおり)

## 理由
1. アドバイスとフィードバックは構造的に1:1であり、Bでは本来不要なUNIQUE制約で
   その1:1をわざわざ担保することになる。Aは制約を書かずに1:1が保証される
2. フィードバック状態はアドバイスを表示するたびに必要になる情報で、同じ行にあるのが
   読み取り経路として最短。既存の`GET /advices/latest`・`GET /advices`のクエリを
   変更せずに済む
3. 現時点で「評価軸が複数ある」「評価の変更履歴を残す」という要求は無い。
   将来それが必要になった時点でBへ移行すればよく、今から分割するのは過剰設計
4. `advices`は完全なイミュータブルではない(7-8で、ユーザーの明示操作時にのみ
   adviceレコードを更新する設計を既に置いている)。したがって
   「AI生成物のテーブルは書き換えない」という原則を新たに破るわけではない

### Bへ移行する条件(将来の判断材料)
以下のいずれかが必要になった時点で、`advice_feedbacks`への移行を再検討する。

- 評価軸が2つ以上になる(例:「役に立った」に加えて「難しすぎた/簡単すぎた」)
- 評価の変更履歴を残す必要が出る
- フィードバックに複数の子レコード(コメントのスレッド化など)がぶら下がる

## 影響
- `docs/database.md`の`advices`テーブル定義に3カラムを追記する
- `docs/api.md`に`PUT /advices/{id}/feedback`を追記する
- `GET /advices/latest`・`GET /advices`のレスポンスにフィードバック関連フィールドが増える
  (未評価時はnull)。既存フィールドの変更は無いため、フロントエンドは後方互換
- フィードバックをAIプロンプトに反映する処理は本ADRのスコープ外(データを貯める段階まで)
