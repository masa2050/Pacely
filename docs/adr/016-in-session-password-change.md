# ADR 016: ログイン中ユーザーのパスワード変更方式

## ステータス
決定済み

## 背景
フェーズ7-4として、設定画面からログイン中のユーザーが自分でパスワードを変更できる機能を追加する。
既存のパスワード再設定機能(docs/adr/010)は「ログインできない状態のユーザーがメールのリンク経由で
新しいパスワードを設定する」フローで、フロントエンドがSupabase Authのセッション
(`supabase.auth.updateUser`)を直接叩くだけで完結していた。

一方、implementation-plan.md 7-4では「BE: Supabase AuthのUpdateUser相当の呼び出しをservice層に
実装する」と明記されている。ADR-010と同じくフロントから`supabase.auth.updateUser`を直接呼ぶだけでも
機能的には動くが、それだとバックエンドの実装が不要になり計画の意図と合わない。また「現在のパスワードを
確認してから変更する」という要件をどこで満たすかも決める必要がある。

## 検討した選択肢

### パスワード変更の実行方法
- **A: フロントエンドから`supabase.auth.updateUser({password})`を直接呼ぶ(ADR-010と同じ)**:
  実装は最小だが、バックエンドのservice層を経由しない。今後「変更履歴を残す」「変更時に通知する」
  といった要件が増えたときにフロント・バックエンド両方に手を入れる必要が出てくる
- **B: バックエンドに新規エンドポイントを設け、Supabase Auth管理者API
  (`PUT /auth/v1/admin/users/{id}`, `service_role`キー使用)経由でパスワードを更新する**:
  退会機能(docs/adr/014)の`DeleteAccount`と同じ「管理者APIをservice層から叩く」パターンを踏襲でき、
  実装イメージが既存コードと一貫する。将来的な拡張(変更ログ等)もバックエンド側に閉じて追加できる

### 「現在のパスワード」の確認方法
- **A: バックエンドでSupabaseのパスワード検証APIを呼んで確認する**: バックエンドがユーザーの
  メールアドレスを別途取得・保持する必要があり、JWTのペイロードにメールが含まれない構成の場合は
  追加の調整が必要になる。個人開発のMVPとしては過剰
- **B: フロントエンドが`supabase.auth.signInWithPassword({email, password: 現在のパスワード})`で
  再認証してから、成功した場合のみバックエンドの変更APIを呼ぶ**: Supabase Auth SDKが本来持っている
  検証機能をそのまま使えるため、バックエンド側に検証ロジックを重複実装せずに済む。ログイン画面
  (AuthForm.tsx)ですでに同じSDK呼び出しを使っており、実装パターンとして自然

## 決定
- パスワード変更本体はB(バックエンド経由、Supabase Auth管理者API)を採用
  - `internal/service/user.go`に`UpdatePassword`を追加し、`DeleteAccount`と同じ
    `PUT /auth/v1/admin/users/{id}`パターンで新しいパスワードを設定する
  - `PUT /users/me/password`(要JWT認証)としてエンドポイントを新設する
- 現在のパスワードの確認はB(フロントエンドでの再認証)を採用
  - 設定画面で「現在のパスワード」「新しいパスワード」の入力を受け取り、まず
    `supabase.auth.signInWithPassword`で現在のセッションのメールアドレス+現在のパスワードを検証する
  - 検証に成功した場合のみ`PUT /users/me/password`を呼び、新しいパスワードをバックエンド経由で設定する
  - 失敗した場合はバックエンドを呼ばず、「現在のパスワードが正しくありません」等のメッセージを表示する

## 理由
1. 管理者APIを使うパターンをDeleteAccountと共通化することで、Supabase Auth関連のバックエンド実装が
   1箇所(service/user.go)に集約され、見通しが良くなる
2. パスワード検証をバックエンドに二重実装せず、Supabase Auth SDKの`signInWithPassword`という
   既存の検証機能に委譲することで、個人開発のMVPとして過剰な実装を避けられる(CLAUDE.md方針4)
3. ADR-010の「メールリンク経由の再設定」とはユーザー導線・呼び出しAPIが明確に分かれるため、
   2つのパスワード変更経路が混同されにくい

## 影響
- `docs/api.md`に`PUT /users/me/password`を追加
- 新規エンドポイントの認証はJWTのみで、リクエストボディに現在のパスワードは含まれない
  (確認はフロントエンドの再認証で完了している前提のため)。バックエンド単体で見ると
  「新しいパスワードを指定すれば誰でも変更できる」ように見えるが、JWT自体が有効なセッションを
  要求するため、他人のパスワードを変更することはできない
