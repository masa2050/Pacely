# ADR 011: 進捗計算は「直近5件の記録の平均ペース」と目標ペースの差分で表す

## ステータス
決定済み

## 背景
フェーズ4(進捗確認機能)で`GET /goals/active/progress`を実装するにあたり、docs/api.md 2.4には「直近の平均ペース、目標ペースとの差分などをバックエンドで計算して返す」とだけ書かれており、具体的な計算範囲は未確定だった。決めるべき点は2つある。

1. 「目標ペース」をどう算出するか(goalsテーブルは`target_time_sec`しか持たず、距離を直接持たない)
2. 「直近の平均ペース」の対象範囲(全記録の平均か、直近何件か)

## 検討した選択肢

### 目標ペースの算出
- **A: goalsテーブルに`target_distance_km`カラムを追加する**: 正確だが、`goal_type`(例: `full_marathon`)から一意に距離が決まるため冗長な情報になる
- **B: `goal_type`文字列から距離(km)への固定マッピングをservice層に持つ**: スキーマ変更不要。GoalForm.tsxの`GOAL_TYPES`(`full_marathon`/`half_marathon`/`10km`/`5km`)と1対1対応するマップをバックエンドに置くだけで済む

### 直近の平均ペースの対象範囲
- **A: 全記録の平均**: 実装は単純だが、直近のコンディション(調子が上がってきた/落ちてきた)を反映しづらい。記録が増えるほど古いデータに引っ張られる
- **B: 直近N件の平均**: 直近の傾向を反映しやすい。Nは`docs/api.md`のadvices生成条件で使われている「3件」とは別概念(あちらは「最低何件あれば提案可能か」の閾値、こちらは「平均を取る対象の窓」)として扱う

## 決定
- 目標ペースはBを採用。`service.goalTypeDistanceKm`にfull_marathon=42.195/half_marathon=21.0975/10km=10/5km=5のマップを持ち、`target_time_sec / distanceKm`で算出する
- 直近の平均ペースもBを採用。直近5件(`recentRunsForProgress = 5`)の`pace_sec_per_km`の単純平均とする
- `GET /goals/active/progress`は有効な目標が無い場合、`GET /goals/active`と同じくErrNotFound→404を返す(進捗は目標があって初めて意味を持つため)
- 記録が1件も無い場合は404にはせず、`recent_average_pace_sec_per_km`/`pace_diff_sec_per_km`を`null`にしたレスポンスを返す。フロント側で「まだ記録がありません」の案内を出す

## 理由
1. `goal_type`→距離のマッピングは値が変わることがほぼ無い固定情報であり、DBに持たせるより定数として持つ方がシンプル(CLAUDE.mdの過剰設計をしない方針に沿う)
2. 直近N件方式は将来AI提案(フェーズ5)のプロンプトに「直近の傾向」を渡す際にも同じ考え方を流用できる
3. 「目標なし」と「記録なし」を別のエラー表現にすることで、フロント側のメッセージ出し分け(「目標を設定してください」/「記録を追加してください」)がそのままレスポンス構造から作れる

## 影響
- 新しい`goal_type`を追加する場合、`GoalForm.tsx`の`GOAL_TYPES`と`service.goalTypeDistanceKm`の両方を更新する必要がある(2箇所に分散している点は将来の改善余地として認識しておく)
- フェーズ5でAI提案のプロンプトに「直近の平均ペース」を渡す場合、このADRの直近5件ロジックをそのまま再利用できないか検討する(重複実装を避けるため)
