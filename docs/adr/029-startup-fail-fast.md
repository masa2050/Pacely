# ADR 029: 起動時に設定・DB・JWKSを確認し、失敗したら起動しない(fail-fast)

## ステータス
決定済み(事後記録)

この判断はフェーズ0(環境構築、DBのPing)とJWT検証の実装時(JWKSの取得)に行い、`cmd/api/main.go`と`internal/config/config.go`の
コメントに理由を書いていたが、ADRとして残していなかった。2026-10-25の障害(`docs/devlog.md`)で
この設計のトレードオフを実際に経験したため、記録する。

## 背景
BEは、DB(Supabase PostgreSQL)・Supabase AuthのJWKS(JWT検証用の公開鍵、ADR005)・
Gemini/OpenWeatherMapのAPIキーがそろって初めて機能する。これらのどれかが欠けたとき、
「サーバーを起動しない」か「起動はして、使う時点でエラーにする」かを決める必要があった。

## 検討した選択肢
- **A: 起動時にすべて確認し、1つでも失敗したら起動しない(fail-fast)(採用)**:
  設定ミスにデプロイ直後のログで気づける。ただし、外部サービス(DB・Supabase Auth)が
  一時的に応答しないだけでも起動できない
- **B: 起動はして、DB接続やJWKS取得は使う時点で行う(遅延初期化)**: 外部サービスが一時的に
  落ちていてもサーバー自体は起動し、復旧すれば自動で使えるようになる。ただし、設定ミスが
  あっても起動に成功してしまい、実際のリクエストで500が返るまで気づけない
- **C: 起動時に確認するが、失敗してもログを出して起動を続け、裏で再試行する**: AとBの中間。
  再試行の間隔・回数・その間のリクエストの扱いを決める必要があり、実装が複雑になる

## 決定
Aを採用する。起動時に以下を順に確認し、失敗したら`log.Fatal`で終了する。

1. 必須の環境変数がそろっているか(`config.Load`): `DATABASE_URL`・`SUPABASE_URL`・
   `SUPABASE_SERVICE_ROLE_KEY`・`GEMINI_API_KEY`・`OPENWEATHERMAP_API_KEY`
2. DBに接続できるか(`pool.Ping`、5秒でタイムアウト)
3. JWKSを取得できるか(`keyfunc.NewDefault`)

起動後のDBの状態は`GET /health`(`db: up / down`)で確認できるようにする。

## 理由
1. 個人開発では、本番の不具合に気づくきっかけがデプロイ直後のログ確認くらいしかない。
   「起動に失敗する」ほうが「起動したが一部の機能だけ500を返す」より圧倒的に気づきやすい
2. 特にAI提案はPacelyの中核機能(CLAUDE.md)であり、APIキー未設定のまま起動して
   `GET /advices/latest`で初めて失敗する、という状態を避けたい
3. Cの再試行の仕組みは、MVPの規模に対して過剰設計になる(CLAUDE.md)

## 影響・トレードオフ
- 2026-10-25の障害では、Supabase側のDBパスワードを先に変えたことで、稼働中のBEが新しい接続を
  張れなくなった(稼働中のプロセスは落ちず、リクエストごとにDB接続エラーになった)。この状態で
  BEが再起動すると、2.のPingで失敗して起動できない。つまりfail-fastは「設定ミスに気づける」一方で、
  「認証情報を入れ替える間は、BE側の値とそろえない限り起動できない」という性質を持つ
- このため、認証情報の入れ替えは「新しい値を用意 → BEに反映して起動を確認 → 古い値を失効」の
  順に行う(ADR027の手順もこれに従う)
- 外部サービスの一時的な障害でも起動できなくなるため、将来、利用者が増えて可用性がより重要に
  なった場合は、Cの再試行方式への変更を検討する
