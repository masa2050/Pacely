# ADR 032: マイグレーションの本番適用は、当面は手動運用を続ける

## ステータス
決定済み

ADR006で「CI/CDに組み込む場合は別途スクリプト化が必要(フェーズ6で検討)」としていた点について、
検討した結果を残す。実際に手動で適用した直近の例は、ADR031(マイグレーション000008)。

## 背景
- マイグレーションのファイルは`backend/migrations/`にあり、2026-11-03時点で8つ(000001〜000008)
- 本番DB(Supabase)への適用は、ローカルから`migrate`コマンドで接続先を本番のSession poolerに向けて
  実行している(`docs/deployment.md`、ADR006、ADR030)
- アプリ本体のデプロイは、`main`へのマージでVercel(FE)とRailway(BE)が自動で行う。つまり
  **デプロイは自動で、マイグレーションの適用だけが手動**になっている
- マイグレーションを自動化すべきか、という問いが出た。CIとは別の話で、検証済みのものを本番へ
  届けるCD(継続的デリバリー)の範囲にあたる
- 適用の順序には制約がある。デプロイ中は、新旧のコードが同時に動く時間があり、DBは1つしか
  ないため、列を足す変更はDBを先に、列を消す変更はコードを先に出す(expand and contract)。
  この順序は、自動化しても変わらない

## 検討した選択肢
- **A: アプリの起動時に実行する**: `main.go`の起動処理で、`golang-migrate`のライブラリを呼ぶ
  (ADR006のBと近い)。手順は少ない。ただしアプリがDBの構造を変える権限を持ち続け、
  マイグレーションが失敗するとアプリが起動しない。`golang-migrate`はBEの依存に加わる
- **B: デプロイの直前に実行する**: Railwayの「デプロイ前に1回だけ実行するコマンド」(Pre-deploy
  Command)で`migrate up`を実行する。アプリのコードは変えずに済む。ただしDockerイメージに
  `migrate`コマンドと`migrations/`を含める必要があり、Railwayでこの設定が使えるかは、
  設定画面で確認が必要(未確認)
- **C: GitHub Actionsから本番DBに実行する**: 本番DBの接続文字列をGitHubのsecretに預ける。
  Railwayのデプロイとは別に動くため、「マイグレーションが先、コードが後」の順序を保証するには、
  別の仕組み(CIの完了を待ってからデプロイする設定など)が要る
- **D: 手動で実行する(採用)**: 今の運用を続ける

## 決定
Dを採用し、当面は手動運用を続ける。自動化する場合の第一候補はBとする(見直す条件は後述)。

## 理由
1. **頻度が低い**: マイグレーションは全体で8つしかなく、変更のたびに数分で終わる作業である
2. **1人開発・環境が1つ**: 手順を引き継ぐ相手も、環境ごとの手順の差もなく、手動の事故が起きにくい
3. **本番DBを、人の目が届かない状態で書き換えない**: 自動化すると、失敗に気づくのが遅れる。
   `golang-migrate`は、途中で失敗すると`dirty`という状態になり、人が内容を確認して復旧する必要がある。
   手動なら、`version`で現在の状態を確認しながら進められる
4. **管理する対象が増えない**: A〜Cは、DB権限を持つコードの増加(A)、Dockerイメージの変更(B)、
   接続文字列の預け先の増加(C)を伴う。今の規模には見合わない(CLAUDE.mdの「過剰設計をしない」)
5. 自動化しても、**順序の判断**(古いコードでも動く変更だけを先に出す)と、**失敗時の復旧**
   (`down`の実行、コードを戻してもDBは戻らない)は、人が考える必要があり、手動の負担の大部分は残る

## 影響・トレードオフ
- **適用を忘れるリスク**が残る。ADR031では、PRの説明文に、「先にDBへマイグレーション、後でマージ」を
  チェックリストとして書いて対応した。DBの変更を含むPRでは、これを必ず書く
- マイグレーションのファイルは、`up`と`down`の両方を書き、ローカルで`up`→`down`→`up`を確認してから出す
  (ADR031で実施)
- 適用後は、`migrate ... version`で番号を確認する。接続文字列は、チャットやコミットに貼らず、
  環境変数に入れて使う
- 手順が、特定の人の手作業に依存する。複数人での開発になった時点で見直す
- **CIでのマイグレーションの検証は、別の話として行う**。手動運用を続けても、CIの中の一時的な
  空のDBに、全マイグレーションを適用して確かめることはできる(CIでDBを使うテストを
  実行する対応で行う)。本番への自動適用とは、分けて扱う

## 見直す条件
次のいずれかが起きたら、このADRを見直す。
- マイグレーションの**適用忘れが原因の事故**が起きた
- マイグレーションの**頻度が増え**、手作業が負担になった
- **複数人で開発する**ようになった、またはステージング環境を追加した
- 本番DBの接続文字列を手元で扱うこと自体が、運用上の問題になった

見直すときは、Bを最初に検討する。その際は、次の点を守る。
- 列の削除など、古いコードを壊す変更は、「コードで使うのをやめる」と「DBから消す」の2回に分けて出す
- 失敗したときの復旧手順(`dirty`の解消、`down`の実行)を、先に`docs/deployment.md`に書く
