# ADR 034: 目標が変わったら、24時間以内でもAI提案を再生成する(goal_idの比較と、24時間3回の上限)

## ステータス
決定済み

## 背景
`GET /advices/latest`(docs/adr/004)は、最新の提案の`generated_at`が24時間以内なら、AIを呼ばずに
その提案をキャッシュとして返す。このとき最新の提案は`GetLatestByUser`で**ユーザー単位**に取っており、
どの目標向けの提案かを見ていない(docs/implementation-plan.md 9-6 課題B)。

そのため次のことが起きる。

1. 目標Aで提案を生成する(10:00)
2. 目標Bを新しく作る(11:00)。docs/adr/009のとおり、Aは自動でabandonedになる
3. ダッシュボードを開くと、放棄済みの目標A向けの提案が表示される(翌10:00まで)

AIコーチが「目標に向けて次に何をすべきか」を示すアプリである以上、設定したばかりの目標に対して、
別の目標向けの提案が出るのは、プロダクトの中核に関わる不具合である。

`GetLatest`の中で「最新の提案が新しいか」を確認する箇所は2つある
(`latestIfFresh`、docs/adr/031)。

- 生成の権利を取る**前**の確認
- 権利を取った**後**の再確認(double-checked locking)

片方だけ直すと、もう片方で古い目標向けの提案が「新しい」と判断されて返ってしまう。

## 検討した選択肢
- **A: 最新の提案の`goal_id`を、現在の有効な目標のIDと比較する(採用)**: `latestIfFresh`に現在の
  目標IDを渡し、`goal_id`が異なれば24時間以内でも「生成が必要」と判断する。DBの変更なし
- **B: 現在の目標の提案だけを取得する**: repositoryに`GetLatestByGoal`を足し、現在の目標に絞って
  最新の提案を探す。`goal_id`がNULLの提案は条件から自然に外れる。ただしrepositoryの関数が増え、
  `GetLatestByUser`との使い分けが必要になる。放棄済みの目標が再びactiveになることは無い
  (docs/adr/009)ため、Aと結果はほぼ変わらず、増える部品に見合う利点が無い
- **C: 目標の作成・編集時に、提案のキャッシュを無効化する**: 目標の編集にも効くが、
  「提案が有効か」を表す列の追加(マイグレーション)が要り、goalのserviceとadviceのserviceが
  結びつく。個人開発のMVPには過剰

Aを採ると、目標を作り直すたびに再生成されるため、24時間に1回という上限が実質的に無くなる。
これへの対策として、次の3つを比較した。

- **X: 制限しない**: 目標の切り替えは頻度が低く、ログイン済みの本人が自分の枠を使うだけである。
  ただし、悪意のあるユーザーが目標の作成を繰り返すと、AI APIの無料枠(全ユーザー共通)を
  使い切れてしまう。また「24時間に1回と言いながら、目標を変えれば外れる」という説明になり、
  設計の一貫性を問われたときに答えにくい
- **Y: 最低間隔(クールダウン、例: 生成から1時間)を設ける**: 目標を間違えて作った場合に、
  正しい目標向けの提案が出るまで待たされる。待つ間は前の目標向けの提案が出るため、課題Bが部分的に残る
- **Z: 24時間あたりの生成回数に上限を設ける(採用)**: 直近24時間の生成が上限回数に達していたら、
  目標が変わっても再生成しない。1〜2回の作り直しなら待たずに再生成され、悪用されても
  1ユーザーあたりの回数は上限で止まる。DBの変更は不要(`advices`の件数を数えるだけ)

## 決定
Aを採用し、Zの回数上限を組み合わせる。

- `latestIfFresh(ctx, userID, goalID)`のように、現在の目標のIDを受け取る
- 次のいずれかなら`(nil, nil)`(=生成が必要)を返す
  - 最新の提案が無い
  - 最新の提案の`generated_at`から24時間以上経っている(従来どおり)
  - **最新の提案の`goal_id`が、現在の目標のIDと異なる**
  - **最新の提案の`goal_id`がNULL**
- 権利を取る前の確認と、権利を取った後の再確認の**両方**に、同じ目標IDを渡す
- **直近24時間に生成した提案が3件(`maxAdviceGenerationsPerWindow`)以上なら、生成せず、
  直前の提案(目標を問わずユーザーの最新の提案)を`status: "ready"`で返す**
  - 数えるのは、生成の権利(docs/adr/031)を取り、再確認を終えた**後**にする。権利を取る前に
    数えると、数えてから保存するまでの間に別のリクエストが割り込み、上限を超えて生成できてしまう
    (ADR031と同じcheck-then-act競合)
  - 「直近24時間」の基準はDBの`now()`に揃える。`generated_at`もDBの`now()`で入るため
- `GET /advices/latest`のレスポンスの形は変えない。`docs/api.md` 3.の処理フローの4.に条件を足す

### 個別の判断
- **`goal_id`がNULLの提案は「目標が違う」扱いにして再生成する**。現在のコードは`goal_id`を必ず
  入れて保存し(`generate`)、`goals`の削除は`ON DELETE CASCADE`(migrations/000005)で提案ごと消えるため、
  NULLが残りうるのは古いデータだけである。どの目標向けか確認できない提案を返すと、今回直す不具合と
  同じ種類の問題が残る。安全側に倒しても、再生成が最大1回増えるだけで済む
- **目標の編集(`PUT /goals/{id}`)は、今回の対象外にする**。編集は`goal_id`を変えずに
  目標タイムや日付だけを書き換えるため、`goal_id`の比較では検出できない。`goals`には`updated_at`が無く、
  検出するにはカラム追加(マイグレーション)が要る。課題Bは「目標の切り替え」に絞る
- **上限は3回**とする。通常の1回に、目標の作り直し(入力の間違いの修正など)2回分の余裕を足した値。
  まずはこの値で運用し、実際の使われ方を見て見直す
- **上限に達したときは、直前の提案を返す**。新しい`status`(「今日の再生成の上限に達しました」など)を
  足す案もあるが、FEの変更が要る。上限に達するのは短時間に目標を3回以上作り直した場合だけで、
  通常の利用では起きないため、まずはFEを変えずに済む方を選んだ。画面での伝え方は、
  docs/implementation-plan.md 9-7 ②(「再読み込み」ボタンの挙動)の検討とあわせて扱う

## 理由
1. 変更がservice層の1関数(`latestIfFresh`)と呼び出し2か所で済み、DBのスキーマも、APIのレスポンスの
   形も変わらない。「過剰設計をしない」方針に合う(CLAUDE.md 開発方針4)
2. `GetLatest`は、冒頭で有効な目標を取得済み(`GetActiveByUser`)で、その`goal.ID`をそのまま使える。
   追加のDBアクセスも発生しない
3. 比較を`latestIfFresh`の中に閉じ込めることで、権利を取る前と取った後の両方に、同じ条件が自動で
   かかる。片方に付け忘れる事故を、関数の引数(目標ID)を必須にすることで防げる
4. 目標が変わったら、24時間を待たずに新しい目標向けの提案を出すことは、ADR004の
   「AI提案を実際に見にいくタイミングでのみ生成する」という考え方と矛盾しない。見にいったときに
   古い目標向けのものしか無いなら、生成する理由がある
5. 24時間キャッシュの本当の目的は「AI APIの呼び出し回数(費用・無料枠)に上限があること」であり、
   「1日1回」という回数そのものではない。目標の変更は再生成の正当な理由として認め、その代わりに
   回数の上限で費用の上限を保証する。上限は常に効いており、「目標を変えれば制限が外れる」わけではない
6. 回数の上限は、待ち時間(クールダウン)と違い、目標を間違えて作り直したユーザーを待たせない

## 影響・トレードオフ
- **1ユーザーあたり、24時間に最大3回までAIが呼ばれうる**(従来は1回)。同時実行は生成リース
  (docs/adr/031)で1件に抑えられ、順番の実行は回数の上限で止まる
- 上限に達したユーザーには、前の目標向けの提案が返りうる(課題Bの症状が、上限まで作り直した場合だけ残る)。
  画面には上限に達したことが表示されない
- 上限は**ユーザー単位**なので、アカウントを大量に作られると防げない。これは今回の変更とは関係なく
  もとからある問題で、必要になったらサインアップの制限やサーバー全体の上限を別に検討する
- **上限の確認は2回行う**。権利を取る前の確認は、上限に達したユーザーが毎回権利を取りにいき、
  生成しないのに書き込みを繰り返す(同時リクエストには「生成中」を返してFEにポーリングさせる)のを
  避ける早期リターンである。権利を取った後の確認が、上限を守る本体である(/code-review指摘)
- /code-reviewで指摘され、今回は直さなかったもの(いずれも頻度が低い、またはもとからある問題)
  - **上限は、保存できた提案だけを数える**。AIの呼び出しが成功しても保存に失敗した場合や、
    AIがエラーを返した場合は数えられない。失敗が続く間は、権利を返すたびに再試行できる。
    これはADR031で「クールダウンを検討する」と書いた問題と同じで、失敗を数える列
    (`users`への試行回数など)が要るため、別のタスクにする
  - **鮮度の判定(`time.Since`)はアプリのサーバーの時計、上限の判定はDBの`now()`**。
    両者がずれると、判定が食い違う窓が生じる。同じDBに繋がるRailway/Supabaseでは、ずれは
    通常数秒以内で、24時間の窓に対して無視できる。ずれが問題になったら、鮮度の判定もDBの
    `now()`に揃える
  - **生成中(最大約100秒)に目標が変わると、古い目標向けの提案が保存・返却される**。生成の
    開始時に目標を読んでいるため。保存される提案の`goal_id`は生成時の目標なので、次の取得では
    目標違いとして再生成される(その分、上限の1回を使う)。生成の直前に目標を読み直す案もあるが、
    目標の作成が生成の最中に重なる場合に限られるため見送った
  - 上限の確認とその後の最新取得は別々のSQLなので、同一のスナップショットではない。
    返す提案が数えた時点と数ミリ秒ずれうるが、提案は追記のみで、上限判定には影響しない
- 「24時間の上限の中で、再生成の正当な理由を認める」という形は、docs/implementation-plan.md 10-3
  (けが・体調の状態入力)でも使える。状態を入力したら24時間以内でも作り直すかを決める際、
  同じ上限(`maxAdviceGenerationsPerWindow`)を共有すれば、再生成の理由が増えても費用の上限は変わらない
- **目標の編集では、24時間以内は古い内容の提案が返る**。たとえば目標タイムを変えても、同じ`goal_id`
  なので提案は取り直されない。編集時にも再生成したくなった場合は、`goals.updated_at`を足して
  `advices.generated_at`と比較する別タスクにする。docs/implementation-plan.md 9-7 ②
  (「再読み込み」ボタンの挙動)の検討でも、「いつ再生成されるか」にこの条件が加わる
- 新しい目標では、`ListRecentByGoal`(docs/adr/021)が`goal_id`で絞り込むため、前の目標の提案は
  「前回までの提案」としてプロンプトに入らない。目標が変わった直後のメニューが、前の目標のメニューに
  引きずられることはない
- 検証: `advice_concurrency_test.go`と同じ構成で、(1)目標を変えると24時間以内でも再生成される、
  (2)`goal_id`がNULLの提案があっても再生成される、(3)目標が同じなら従来どおりキャッシュを返す、
  (4)権利を取った後の再確認でも同じ条件が効く(古い目標向けの提案を「新しい」と返さない)、
  (5)目標の切り替えを繰り返しても生成は3回までで、4回目は直前の提案を返す、ことを確認する
- ADR004・ADR031、`docs/api.md` 3.、`docs/implementation-plan.md` 9-6を更新する
