# ADR 028: FE-BE間のAPI方式にREST(JSON over HTTPS)を採用

## ステータス
決定済み(事後記録)

この判断はプロジェクト初期(API設計時)に行い、`docs/api.md`の冒頭に一行で理由を書いていたが、
ADRとして残していなかった。番号は記録した順に振る運用のため、決定時期より後の番号になっている。

## 背景
FE(React、Vercel)とBE(Go + Echo、Railway)の間の通信方式を決める必要があった。
扱うデータは「記録」「目標」「AI提案」「ユーザー」といったリソースのCRUDが中心で、
画面ごとに必要なデータの形もほぼ固定されている。

## 検討した選択肢
- **REST(JSON over HTTPS)(採用)**: リソースとHTTPメソッドの組み合わせで設計する。ブラウザから
  `fetch`でそのまま呼べ、curlやブラウザの開発者ツールで確認しやすい
- **gRPC**: インターン(ADR001)で実務経験がある。型定義(.proto)から通信コードを生成でき、
  サービス間通信では高速。ただしブラウザから直接は呼べず、gRPC-Webとプロキシが追加で必要になる
- **GraphQL**: FEが必要な項目だけを1回で取得できる。ただしスキーマ・リゾルバの仕組みを導入する
  必要があり、画面ごとに取得するデータが固定されているMVPでは、利点に対して導入コストが大きい

## 決定
RESTを採用する。エンドポイント一覧は`docs/api.md`に記載する。

## 理由
1. 呼び出し元がブラウザのみで、追加のプロキシや生成ツールなしで呼べるRESTが最も単純
   (CLAUDE.md「過剰設計をしない」)
2. データがリソースのCRUD中心で、RESTの「リソース + HTTPメソッド」の設計に素直に当てはまる
3. インターンではgRPCを使っていたため、あえてRESTを選んだ判断を含めて、両者の違い・使い分けを
   説明できるようにする(`docs/api.md`冒頭)

## 影響
- `GET /advices/latest`はGETだが副作用(AI呼び出し・DB書き込み)を持たせている。RESTの原則からは
  外れるが、意図的な例外としてADR004に記録している
- 将来、複数のバックエンドサービス間で通信が必要になった場合は、その区間に限ってgRPCを検討する余地がある
