# ADR 005: JWT検証はSupabaseの公開鍵(JWKS/ES256)方式を採用

## ステータス
決定済み

## 背景
バックエンドでSupabase Auth発行のJWTを検証する必要があった。当初はSupabaseの「JWT Secret」(共有シークレット)を使うHS256方式で実装したが、実際に発行されたトークンで検証すると常に失敗した。トークンのheaderを確認したところ`alg: ES256`(非対称鍵署名)であり、想定していた方式と異なっていた。

## 検討した選択肢
- **A: HS256 + 共有シークレット(`SUPABASE_JWT_SECRET`)**: 実装が単純(1つの秘密鍵をそのまま検証に使う)。ただし今回作成したSupabaseプロジェクトはこの方式でトークンを発行しておらず、そもそも検証が通らない
- **B: ES256 + JWKS(公開鍵)**: Supabase Auth が実際に使っている方式。`{SUPABASE_URL}/auth/v1/.well-known/jwks.json` から公開鍵を取得し、それで署名検証する。鍵ローテーションに追従するため定期的な再取得が必要になる

## 決定
Bを採用する。`github.com/MicahParks/keyfunc/v3` でJWKSを取得・定期リフレッシュし、`golang-jwt/jwt/v5` の `WithValidMethods(["ES256"])` でアルゴリズムを固定して検証する。

## 理由
1. Supabaseの実際のトークン発行方式に合わせる必要があり、そもそも選択の余地がなかった(新規Supabaseプロジェクトのデフォルトが非対称鍵方式のため)
2. 公開鍵方式は秘密鍵をバックエンドに置かずに済み、鍵漏洩時の影響がHS256の共有シークレットより小さい
3. `alg`をES256に固定することで、JWT実装で知られるアルゴリズム混同攻撃(`alg`を`none`や別方式に書き換える攻撃)を防ぐ

## 影響
- `SUPABASE_JWT_SECRET`環境変数は不要になった。代わりに`SUPABASE_URL`からJWKS URLを導出する
- JWKS取得はネットワーク呼び出しを伴うため、起動時に取得失敗するとサーバが起動しない(意図的なfail-fast)
- 面接で聞かれうる想定質問: 「HS256とES256(RS256)の違いと使い分け」「なぜアルゴリズムを検証時に固定するのか」
