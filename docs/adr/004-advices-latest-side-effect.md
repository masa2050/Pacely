# ADR 004: AI提案の生成トリガーをGET /advices/latestに持たせる

## ステータス
決定済み

## 背景
AI提案(アドバイス・練習メニュー)をいつ生成するかを決める必要があった。記録追加時(POST /runs)にトリガーする案と、AI提案取得時(GET /advices/latest)にトリガーする案を比較した。

## 検討した選択肢
- **A: POST /runs時に生成判定する**: 記録追加のたびにAI生成要否を判定する。記録エンドポイントの責務が増える
- **B: GET /advices/latest時に生成判定する**: 取得時に「前回生成から24時間経過しているか」「記録が3件以上あるか」を判定し、必要な場合のみ生成する。GETリクエストに副作用(外部API呼び出し・DB書き込み)を持たせることになり、一般的なREST設計原則からは外れる

## 決定
Bを採用する。GET /advices/latestが生成判定・生成処理までを担う。

## 理由
1. POST /runsをシンプルなDB書き込みのみの処理に保てる
2. AI提案を実際に見にいくタイミングでのみ生成すればよく、ユーザーがアプリを開かない日に無駄な生成が走ることを防げる(コスト最適化)
3. GETに副作用を持たせる設計はRESTfulの原則には反するが、個人開発でのAPI呼び出し回数最小化という実利を優先した意図的なトレードオフである

## 影響
- 「なぜGETなのに副作用があるのか」を説明できるようにしておく必要がある(面接で設計思想を問われた場合の想定質問)
- 将来的にリクエスト数が増え、レスポンス速度が問題になった場合は、生成処理を非同期化(キューイング)する設計への変更を検討する
