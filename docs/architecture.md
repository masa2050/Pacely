# Pacely アーキテクチャ設計書

## 1. 技術スタック(確定)

| 領域                  | 技術                                                                         | 理由(要約)                                                                                                                                                                                                                                                   |
| --------------------- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| フロントエンド        | React + TypeScript                                                           | 学習価値・求人での需要ともに高い。Vercelとの相性も良い                                                                                                                                                                                                       |
| バックエンド          | Go                                                                           | インターン経験があり就活で語りやすい。シンプルな文法で個人開発・AI駆動開発と相性が良い                                                                                                                                                                       |
| Webフレームワーク(Go) | Echo                                                                         | 標準net/httpよりルーティング・ミドルウェアが書きやすく、学習コストも低い。Ginとの比較でもシンプルさを優先                                                                                                                                                    |
| DB                    | PostgreSQL                                                                   | リレーショナルなデータ(ユーザー・記録・目標)を扱うのに適している。将来の拡張にも強い                                                                                                                                                                         |
| DBホスティング        | Supabase                                                                     | PostgreSQL + 認証機能をセットで提供。無料枠が個人開発に十分                                                                                                                                                                                                  |
| 認証                  | Supabase Auth(メール/パスワード)                                             | 自前実装よりセキュリティリスクを抑えつつ、認証の仕組み自体は理解して使う                                                                                                                                                                                     |
| AI API                | Gemini API(開発・検証時) → 本番前にClaude/OpenAIと出力品質を比較して最終決定 | Anthropic/OpenAIには恒久的な無料枠がなく、開発初期のコストを避けるためGeminiの無料枠(Flash系モデル)で試作・プロンプト設計を進める。無料枠は入力データがGoogleのサービス改善に利用される規約のため、本番運用では有料ティアまたは他社APIへの切り替えを検討する |
| 天候API               | OpenWeatherMap                                                               | 無料枠が大きく個人開発の定番                                                                                                                                                                                                                                 |
| フロントデプロイ      | Vercel                                                                       | Reactデプロイが容易、無料枠で個人開発は完結                                                                                                                                                                                                                  |
| バックデプロイ        | Railway                                                                      | Dockerで簡単デプロイ、料金上限が予測しやすい                                                                                                                                                                                                                 |

## 2. システム構成図(概要)

```
[ユーザー]
   │
   ▼
[React + TypeScript (Vercel)]
   │  REST API (HTTPS)
   ▼
[Go API サーバー (Railway)]
   │            │             │
   ▼            ▼             ▼
[PostgreSQL   [Claude API]  [OpenWeatherMap API]
 (Supabase)]
```

- フロントエンドはGoバックエンドとのみ通信する(Claude APIや天候APIに直接アクセスしない)
- AI呼び出し・天候取得はすべてバックエンド経由で行う。理由: APIキーをフロントに露出させないため、かつAI呼び出し頻度(日次キャッシュ)をバックエンドで一元管理するため

## 3. レイヤー構成(バックエンド)

個人開発でMVPを早く完成させる方針のため、過剰なレイヤー分割はしない。最低限の責務分離のみ行う。

```
handler(HTTPリクエスト受付・レスポンス整形)
   ↓
service(ビジネスロジック: 目標との差分計算、AI呼び出しの要否判断など)
   ↓
repository(DBアクセス)
```

- ドメイン駆動設計(DDD)のような厳密な層分けは行わない。3層構成で十分
- 将来的に複雑化した場合のみ、必要な箇所を追加でリファクタリングする方針

## 4. データフロー: AIアドバイス生成の仕組み

これがPacelyの中核なので、明確にしておく。

1. ユーザーがランニング記録を新規追加する
2. バックエンドが「直近のAI提案がいつ生成されたか」を確認する
3. 未生成、または最終生成から24時間以上経過している場合のみ、以下を実行:
   a. ユーザーの記録・目標データをDBから取得
   b. 天候情報を取得(ユーザーが選択した地域)
   c. Claude APIにプロンプトを投げてアドバイス・練習メニューを生成
   d. 生成結果をDBに保存(キャッシュ)
4. フロントエンドからの取得リクエストには、常にDBに保存済みの最新のAI提案を返す(リアルタイム生成はしない)

これにより「毎回AIを呼ぶことによるコスト増大」を防ぎつつ、記録更新に応じた提案の鮮度も保てる。

## 5. 認証・認可の方式

- Supabase Authでユーザー登録・ログインを行い、JWTを発行する
- フロントエンドはJWTをリクエストヘッダーに付与してバックエンドAPIを呼ぶ
- バックエンドはJWTを検証し、リクエストのuser_idと、操作対象データのuser_idが一致するかを都度チェックする(他人の記録を操作できないようにする)

## 6. 環境構成

MVPでは環境を分けすぎない。

| 環境     | 用途                                                                                                        |
| -------- | ----------------------------------------------------------------------------------------------------------- |
| ローカル | 開発用。Docker ComposeでGo + PostgreSQL(Supabaseのローカルエミュレータ、または素のPostgreSQLコンテナ)を起動 |
| 本番     | Vercel(FE) + Railway(BE) + Supabase(DB)                                                                     |

ステージング環境は個人開発の規模では不要と判断し、作らない。

## 7. 将来の拡張を見据えた設計方針

- AI呼び出し部分をservice層に閉じ込めておくことで、将来モデルやプロバイダ(OpenAI等)を変更しても影響範囲を限定できる
- repository層をインターフェースで抽象化し、DB変更時の影響を抑える(ただし過剰な抽象化はしない。実装は具体的なPostgreSQL実装のみで良く、インターフェース定義だけ用意する程度に留める)
