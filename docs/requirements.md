# Pacely 要件定義書

## 1. プロダクトの目的

Pacelyは、ランニング記録アプリではなく「AIランニングコーチアプリ」である。
記録の蓄積そのものではなく、**「目標に対して次に何をすべきか」をAIが提案すること**が価値の中心。この前提を外れる機能は原則MVPに含めない。

### 差別化ポイント
- 単なる記録アプリ(Strava/RunKeeper簡易版)や単なるTodoアプリとの違いは、AIによる目標逆算型の提案にある
- この機能を削るとPacelyの存在意義がなくなるため、AI提案機能は最優先で実装する

## 2. ペルソナ

作り込みすぎず、機能の要否判断の基準として1人分定義する。

| 項目 | 内容 |
|---|---|
| 属性 | 20代後半〜40代の市民ランナー |
| ランニング頻度 | 週3〜4回、1回5〜10km程度 |
| 目標 | フルマラソンで自己ベスト更新(例: サブ3.5) |
| 課題 | 練習メニューを自己流で組んでおり、これで目標に届くか不安。専門のコーチをつける余裕はない |
| Pacelyに求めること | 記録をつけるだけでなく、「次に何を走ればいいか」の具体的な指針が欲しい |

このペルソナから導かれる判断基準:
- GPSでの自動計測より、まず「目標逆算のアドバイス精度」を優先する
- 週数回の利用が前提なので、AI提案は毎アクセスのリアルタイム生成ではなく、日次更新で十分

## 3. MVPスコープ

### 3.1 必須機能(MVP)

| 機能 | 概要 |
|---|---|
| ユーザー認証 | メール/パスワードによる登録・ログイン。記録をユーザーごとに紐づけるために必須 |
| ランニング記録(手動入力) | 距離・時間・日付を入力。ペースは距離と時間から自動計算 |
| 記録一覧・履歴確認 | 過去の記録をリスト・簡易グラフで表示 |
| 目標設定 | 種目(フルマラソン等)・目標タイム・目標日を設定 |
| 目標に対する進捗確認 | 現在のペース・走行距離の推移から、目標との差分を簡易表示 |
| AIアドバイス | 記録と目標をもとに、次に取るべき行動をAIが日次で生成・保存 |
| AI練習メニュー提案 | 直近の記録傾向をもとに、次回の練習内容(距離・ペース目安)を提案 |
| 天候考慮(簡易) | ユーザーが選択した地域の天気予報を取得し、AI提案に反映(例:「明日は高温注意」) |

### 3.2 MVPでは実装しない機能

| 機能 | 理由 |
|---|---|
| GPSによる自動計測 | ブラウザでの位置情報常時取得は精度・バッテリー・実装コストの問題が大きく、MVPの本質(AI提案)と直接関係しない |
| Strava/Garmin等の外部連携 | OAuth連携の実装コストが高く、優先度が低い |
| ソーシャル機能(フォロー・共有) | コア価値と無関係。学習コスト対効果が低い |
| プッシュ通知 | Webアプリの範囲を超え、インフラ・実装コストが増す |
| 複数目標の同時管理 | MVPでは目標は1件のみで十分。UI/DB設計をシンプルに保つ |

### 3.3 将来的に追加できる機能

- GPSによる自動計測、ランニングマップ表示
- Strava/Garmin連携によるデータ取り込み
- 練習メニューのカレンダー表示・リマインド
- AIとのチャット形式での相談機能
- 複数目標・レース戦略の管理

## 4. コールドスタート対応方針

記録が少ない新規ユーザーに対して、AIが根拠のない一般論を返すのを防ぐための方針。

- **記録3件未満**: AI提案は「まず◯件記録してください」という汎用ガイダンスを表示し、AI API呼び出しは行わない(コスト削減にもなる)
- **記録3件以上**: 通常のAI提案(個別化されたアドバイス)を有効化する
- 目標が未設定の場合も同様に、「まず目標を設定してください」という導線を出す

## 5. AI呼び出しの方針(コスト・UX観点)

- AIアドバイス・練習メニュー提案は、**ユーザーがアクセスするたびにリアルタイム生成しない**
- 1日1回(または記録が新規追加されたタイミング)で生成し、DBに結果を保存してキャッシュとして返す
- これによりAPI費用を予測可能な範囲に抑え、レスポンス速度も安定させる
- AI APIには月次の利用上限(spending limit)を必ず設定する

## 6. 天候情報の扱い(MVP範囲)

- 位置情報の自動取得(Geolocation API)は行わず、**ユーザーが都道府県/都市を手動選択**する方式にする
- 実装・UXをシンプルに保ち、権限まわりの複雑さを避ける
- 天候APIは無料枠のあるサービスを利用する

## 7. 非機能要件

- **セキュリティ**: パスワードはハッシュ化して保存。ユーザーは自分の記録・目標のみ閲覧・編集可能(認可の実装必須)
- **コスト**: DB・BE・FEは無料枠内での運用を基本とし、AI APIのみ利用上限を設定して従量課金を管理する
- **保守性**: 個人開発として過剰設計は避けるが、後から技術変更しても大きな手戻りにならない程度の疎結合は意識する

## 8. スコープ外の明確化(繰り返し確認用)

以下はMVPの範囲外であることを明記し、実装中に scope creep が起きないようにする:
- ソーシャル機能全般
- GPSリアルタイム計測
- 外部サービス連携(Strava等)
- 複数目標管理
- ネイティブアプリ化
