# Pacely API設計書

## 1. 設計方針

- REST APIとする(既存のインターン経験でREST/gRPCの違いを説明できるため、あえてRESTを採用する判断も含めて語れるようにする)
- 認証はJWT(Supabase Auth発行)をAuthorizationヘッダーで受け取り、全エンドポイントで検証する(ヘルスチェック等を除く)
- レスポンスはJSON形式で統一
- AI提案の生成トリガーは**GET /advices/latest 呼び出し時にチェックする**(記録追加時ではなく取得時)。これにより`POST /runs`はDB書き込みのみのシンプルな処理に保てる

## 2. エンドポイント一覧

### 2.1 認証

認証(サインアップ・ログイン)自体はSupabase Auth SDKをフロントエンドから直接呼び出す想定のため、Pacelyバックエンド側に認証専用エンドポイントは作らない。バックエンドはJWTの検証のみ行う。

| 項目     | 内容                                                                                                     |
| -------- | -------------------------------------------------------------------------------------------------------- |
| 検証方法 | リクエストヘッダーの`Authorization: Bearer <JWT>`をミドルウェアで検証し、user_idをコンテキストに格納する |

### 2.2 ランニング記録(runs)

| メソッド | パス       | 概要                                                                                                                  |
| -------- | ---------- | --------------------------------------------------------------------------------------------------------------------- |
| POST     | /runs      | 記録を新規作成。distance_km, duration_sec, run_date, rpe(任意)を受け取り、pace_sec_per_kmはバックエンドで計算して保存 |
| GET      | /runs      | 自分の記録一覧を取得(クエリパラメータで期間絞り込み可: `?from=&to=`)                                                  |
| GET      | /runs/{id} | 記録の詳細取得                                                                                                        |
| PUT      | /runs/{id} | 記録の修正(入力ミス訂正用)                                                                                            |
| DELETE   | /runs/{id} | 記録の削除                                                                                                            |

### 2.3 目標(goals)

| メソッド | パス               | 概要                                                                                                                                                                            |
| -------- | ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| POST     | /goals             | 新規目標を作成。作成時、既存のactive目標があればバックエンド側でstatusをabandonedまたはachievedに更新してから新規作成する(同時に有効な目標は1件のみという制約をservice層で担保) |
| GET      | /goals             | 自分の目標一覧(履歴含む)を取得                                                                                                                                                  |
| GET      | /goals/active      | 現在有効な目標(status=active)を1件取得                                                                                                                                          |
| PUT      | /goals/{id}        | 目標の編集(目標タイム変更など)                                                                                                                                                  |
| PATCH    | /goals/{id}/status | statusの更新(達成/断念のマーク付け)                                                                                                                                             |

### 2.4 進捗(progress)

| メソッド | パス                   | 概要                                                                                                     |
| -------- | ---------------------- | -------------------------------------------------------------------------------------------------------- |
| GET      | /goals/active/progress | 現在の目標に対する進捗サマリを取得(直近の平均ペース、目標ペースとの差分などをバックエンドで計算して返す) |

### 2.5 AI提案(advices)

| メソッド | パス            | 概要                                                                                                                                                                                                                                              |
| -------- | --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET      | /advices/latest | 最新のAI提案を取得。**このタイミングで「前回生成から24時間以上経過しているか」「記録が3件以上あるか」を判定し、条件を満たせばAI呼び出し→DB保存→結果を返す。満たさなければ既存のキャッシュ、または「記録を増やしてください」等のガイダンスを返す** |
| GET      | /advices        | 過去のAI提案履歴一覧を取得                                                                                                                                                                                                                        |
| PUT      | /advices/{id}/feedback | 表示中のAI提案に「役に立った/役に立たなかった」+任意コメントを送信する。上書き可能(冪等)。他ユーザーの提案は403、存在しないidは404(フェーズ7-5、docs/adr/019) |

### 2.6 ユーザー設定(users)

| メソッド | パス               | 概要                                                                                     |
| -------- | ------------------ | ----------------------------------------------------------------------------------------- |
| GET      | /users/me          | 自分のプロフィール(region・usernameなど)を取得                                            |
| PUT      | /users/me          | region・usernameの更新。どちらか一方のみの送信も可(未送信のフィールドは変更しない)。空文字を送るとその項目を未設定に戻す |
| PUT      | /users/me/password | ログイン中ユーザーのパスワード変更(要:フロントで現在のパスワードを再認証済みであること、docs/adr/016) |
| DELETE   | /users/me          | 退会。Pacely独自データ(runs/goals/advices含む)とSupabase Authアカウントを削除する(docs/adr/014) |

## 3. GET /advices/latest の処理フロー(重要)

これがバックエンドの中で最も複雑な処理になるため、明記しておく。

```
1. リクエストからuser_idを取得
2. DBから直近のadviceレコードを1件取得
3. 以下のいずれかに該当する場合、生成をスキップしてガイダンスメッセージを返す:
   - runsの件数が3件未満
   - goals.status=activeのレコードが存在しない
4. 上記に該当せず、かつ
   - adviceが1件も存在しない、または
   - 最新adviceのgenerated_atから24時間以上経過している
   場合のみ、以下を実行:
   a. 直近の記録・現在の目標をDBから取得
   b. users.regionをもとに天候APIを呼び出す
   c. Claude APIにプロンプトを投げてアドバイス・practice menuを生成
   d. 結果をadvicesテーブルに保存
   e. 保存した内容をレスポンスとして返す
5. 上記条件に該当しない場合は、既存の最新adviceレコードをそのまま返す(AI APIは呼ばない)
```

- この判定ロジックはservice層に置き、handlerからはシンプルに呼び出すだけにする
- GETリクエストなのに副作用(DB書き込み・外部API呼び出し)が発生する点は一般的なREST設計としては例外的だが、個人開発のシンプルさとAPI呼び出し回数の最小化を優先した意図的な設計判断として、CLAUDE.md・実装時のコメントに明記しておく

### 3.1 PUT /advices/{id}/feedback

リクエストボディ:

```json
{ "is_helpful": true, "comment": "ペースが少しきつかった" }
```

- `is_helpful`: 必須。true=役に立った / false=役に立たなかった。未送信は400
- `comment`: 任意。最大500文字。空文字・空白のみはコメント無し(null)として保存する
- レスポンスは更新後のadviceレコード(フィードバック3カラムを含む)
- 評価の取り消し(未評価に戻す)はスコープ外。押し直しによる上書きで対応する(docs/adr/019)

## 4. エラーレスポンス方針

過剰なエラーコード設計はせず、シンプルに統一する。

| ステータスコード | 用途                                                  |
| ---------------- | ----------------------------------------------------- |
| 400              | バリデーションエラー                                  |
| 401              | 未認証・JWT不正                                       |
| 403              | 他ユーザーのデータへのアクセス試行                    |
| 404              | リソースが存在しない                                  |
| 500              | サーバー内部エラー(AI API・天候APIの呼び出し失敗含む) |

レスポンスボディは `{ "error": "メッセージ" }` の形式で統一する。
